# SPA architecture (no Inertia)

- This application is a traditional first-party Svelte SPA. Do not introduce Inertia packages, middleware, `Inertia::render()`, `Route::inertia()`, or `@inertiajs/*` APIs.
- Client routing is owned by **sv-router** under `resources/js/router`. Laravel serves `resources/views/app.blade.php` via `SpaController` for frontend refreshes.
- Keep `/api/*`, `/sanctum/*`, `/up`, `/email/*`, `/storage/*`, and Fortify endpoints outside the SPA catch-all. Use prefix-boundary-safe exclusions (`api(?:/|$)`, not bare `api`).
- Use Sanctum cookie/session SPA authentication with Axios (`resources/js/lib/http.ts`). Never store auth tokens in `localStorage` / `sessionStorage`. Never introduce JWT or bearer-token auth for the first-party SPA.
- Use Fortify headless (`views => false`) for authentication capabilities (login, register, password reset, email verification, 2FA, password confirmation, profile/password updates). App-owned JSON APIs belong under `/api/v1/...`. Destructive account deletion uses web `DELETE /settings/profile` so the session can be invalidated.
- Auth current-user bootstrap has **one owner**: `startBootstrap()` in `resources/js/auth/auth.svelte.ts` (started from `App.svelte`). Cold load must issue `GET /api/v1/user` exactly once. Guards, layouts, and pages consume `useAuth()` / auth module state. Call `refreshUser()` only after auth/profile mutations. Do not fetch `/api/v1/user` from route guards.
- Route guards must `await waitForAuthReady()` and then redirect. Never `return false` from `beforeLoad` while bootstrapping — that cancels the initial hard-refresh match and leaves a blank page.
- Auth state uses Svelte 5 module runes in `.svelte.ts` (same pattern as `theme.svelte.ts`). Do not add a state-management library unless there is a demonstrated need.
- Global `AppLoader` is for **auth/application bootstrap only**. Page data loading uses skeletons/content placeholders. Mutations use local button/control progress. Do not show the global loader for normal client navigations.
- HTTP 419 (CSRF/session expiry) is normalized by the HTTP layer. Do **not** globally auto-replay failed mutations after 419.
- HTTP 423 (password confirmation) is normalized only. Handle it contextually in sensitive callers — never as a global Axios redirect.
- Two-factor secrets, QR payloads, and recovery codes are Fortify-owned and must never be logged, stored in browser storage, or included on the current-user endpoint / `UserResource`.
- Passkeys: study the official Svelte kit's Fortify + `@laravel/passkeys` approach, but SPA passkey UI is deferred. Do not enable Fortify `Features::passkeys()` until that phase. Leave migrations/docs as intentional deferral notes.
- Wayfinder: generated output lives in `resources/js/actions`, `resources/js/routes`, and `resources/js/wayfinder` (gitignored). Regenerate with `npm run wayfinder:generate` or via the Vite Wayfinder plugin during `dev`/`build`. Runtime source may import generated files; fresh consumers regenerate them — do not commit generated output.
- Boost/agent state (`boost.json`, `AGENTS.md`, `.cursor`, etc.) is author-local and gitignored. Never require `php artisan boost:update` in Composer lifecycle scripts. Boost remains optional (`composer require-dev`); consumers run `php artisan boost:install` when desired.
- Vitest loads `vite.config.*` with a non-build command. Scope `LARAVEL_BYPASS_ENV_CHECK` to `process.env.VITEST` only (and svelte-check). Do not set it globally in CI. For Node >= 25, Vitest workers may need `execArgv: ['--no-webstorage']`.
- Auth form state uses `createForm()` in `resources/js/lib/form.svelte.ts` (Svelte 5 runes). Prefer this over a third-party form library. Preserve normalized HTTP errors from `resources/js/lib/http.ts`. Auth mutations go through `resources/js/lib/auth-api.ts` — do not scatter Axios calls across pages.
- **Validation field spacing convention:** each field is a parent unit `div.grid.gap-2` containing, in order: `Label` → control (`Input` / `PasswordInput` / OTP) → `InputError`. The parent `gap-2` owns vertical spacing. `InputError` must not add its own top margin. Outer auth forms use `flex flex-col gap-6` (and nested `grid gap-6` for field groups). Wire `for`/`id`, `aria-invalid`, and `aria-describedby` via `fieldErrorId` / `fieldDescribedBy`; `InputError` uses `role="alert"`.
- Appearance foundation (light/dark/system) lives in `theme.svelte.ts` + Blade FOUC script + `appearance` cookie. Do not invent a competing theme store. The Appearance settings screen only drives that store — it must issue no API calls.
- Application shell and settings screens are implemented. Shell: `components/AppShell.svelte` (SidebarProvider; the sidebar restores its collapsed state from the `sidebar_state` cookie) + `AppSidebar` / `AppSidebarHeader` / `Breadcrumbs` / `NavMain` / `NavUser` / `UserMenuContent`, composed by `layouts/AppLayout.svelte` → `layouts/app/AppSidebarLayout.svelte`. Navigation uses plain `<a href>` with `p()` from `@/router` — there is no Inertia `Link`. `Toaster` is mounted once in `App.svelte`; do not add another in a layout. The router shell `router/AppShell.svelte` stays a bootstrap loader only.
- Settings mutations live in `resources/js/lib/settings-api.ts` (profile, password, account deletion, security state, 2FA); `auth-api.ts` stays focused on authentication. Do not scatter Axios calls across pages. Every mutation calls `ensureCsrfCookie()` first.
- `refreshUser()` runs after a successful profile update only. Password updates and 2FA enable/disable do not touch `UserResource`, so they must not refresh the current user. Account deletion calls `clearUser()` (the session is already invalidated) and never refetches.
- The validation field spacing convention applies to settings forms exactly as it does to auth forms.
- Security settings page owns its `securityState` and loads in order: password-confirmation status → (redirect to `/confirm-password` when unconfirmed) → `GET /api/v1/settings/security`. It renders a page-level `Skeleton` while loading — never the global `AppLoader`. Sensitive 423 responses are handled with `navigateToConfirmPasswordIfRequired()` from `lib/navigation.ts`.
- Recovery codes are lazy: `TwoFactorRecoveryCodes` must never fetch on mount (the official Inertia kit does — do not copy it). Codes are fetched on the explicit "View" click, reused from memory when hidden and shown again, re-fetched after regeneration, and cleared when `ManageTwoFactor` is destroyed.
- Account deletion is allowed for unverified users; the request invalidates the session and the SPA returns to `/`.
